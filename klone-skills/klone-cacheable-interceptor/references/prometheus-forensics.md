# Метрика кеша в проде — как читать `klone_cache_size_by_tag`

Нужно, когда график в Прометеусе выглядит как утечка памяти или как непонятная пила.
Для обычной работы с `@Cacheable` этот файл не нужен.

## Почему `sum by (tag)` вводит в заблуждение

`Cache` — **in-memory, per-JVM** хранилище: у каждого инстанса (в проде это десятки серверов
× несколько параллельно живущих версий игры, т.е. сотни независимых процессов) свой
собственный стор. Prometheus добавляет к каждой метрике label `instance` при скрейпе,
поэтому `sum by (tag) (...)` складывает значения **по всем инстансам сразу** — это не
состояние одного процесса.

## Два паттерна на графике

- **Пилообразный с резкими обвалами** (пример: `MONETIZATION_TOOL`) — по этому тегу реально
  происходят инвалидации: кто-то жмёт Refill-кнопку или меняет конфиг в туле, все инстансы
  синхронно чистят кеш (Hazelcast-рассылка, см. основной скилл, раздел про инвалидацию),
  дальше lazy-fill до следующего обвала.

- **Плавный монотонный рост, выходящий на плато** (пример: `COMMUNITY_NEWS`, когда давно не
  жали «Update news») — это **не утечка**, а lazy-fill метода `byId(Criteria)`, единственного
  `@Cacheable`-метода, который не прогревается ни `DynamicItemCacheComposer.compose()`, ни
  `PrometheusDynamicItemsMetrics`. `allItems`/`allDynamicItems` плоские с первых секунд —
  растёт именно `byId`, по мере того как трафик игроков покрывает пространство `(version, id)`.
  Выполаживание = пространство исчерпалось (версии фиксированы, `id` — конечный набор).

## Почему пространство ключей `byId` конечно

Боевой вызывающий: `ItemDeserializer.getItem()` → `ItemsProvider.findById(version, itemId)`
(default-метод) → `byId(Criteria.builder().version(version).id(itemId).build())`.
Срабатывает при десериализации стейта игрока, если ссылка на айтем не нашлась среди статичных
XML-айтемов и не в `removedIds`/deprecated.

`userId`/`sig` в `Criteria` при этом **всегда null** — проверено по всей кодовой базе:
`Criteria.builder()` для `byId()` встречается только в `ItemIdToItemMapper` и в этом
`findById()`, оба раза без `userId`. Значит ключевое пространство ограничено `(version, id)`:
рост конечен, но набирается постепенно, по мере разнообразия трафика через конкретный инстанс.

## Как отличить реальную утечку от нормального lazy-fill

Не трогая код:

- `sum by (tag, instance) (...)` — растёт число `instance`-серий → это раскатка/скейлинг,
  а не рост кеша внутри процесса.
- `count(klone_cache_size_by_tag{tag="..."})` — если кривая повторяет форму исходного графика,
  рост суммы объясняется количеством таргетов, а не данными.
- `max by (tag) (...)` — максимум по инстансам стабилен, а `sum` растёт → дело в количестве
  инстансов.
- Ни один из запросов не объясняет рост → подозревай `@Cacheable`-метод с неограниченным
  пространством ключей. Классика: `Criteria` с реальным `userId`/`sig`, меняющимися на каждый
  запрос — каждый вызов создаёт запись, которая никогда не переиспользуется и не удаляется
  иначе как `cache.remove(tag)` целиком.

## Ограничение текущей метрики

`PrometheusCacheMetrics` бьёт метрику по тегу и классу, но **не по имени метода**:
`SignatureKey.functionName` существует, но в лейблы не выведен. Поэтому разделить на графике
вклад `byId` и `allItems`/`allDynamicItems` сейчас нельзя — только по косвенным признакам
(форма кривой) из разделов выше.
