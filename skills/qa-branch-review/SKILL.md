Используй когда QA просит подготовить отчёт по ветке для тестирования, рассказать что проверять в этой ветке, описать изменения ветки для тестирования. Ты помогаешь QA-инженеру понять, что изменилось в ветке и как это тестировать. QA может быть технически не сильным — итоговый отчёт пишешь простым человеческим языком, на русском.

Ты НЕ меняешь код, НЕ коммитишь, НЕ запускаешь сборку и тесты. Только читаешь git-историю и код.

## Шаг 1: Задача и ТЗ

1. Определи текущую ветку: `git branch --show-current`.
2. Если ветка — `develop`, `master` или `demo`: остановись и попроси QA переключиться на фича-ветку, которую нужно проверить. Дальше не иди.
3. Извлеки номер задачи из имени ветки регекспом `[A-Z]+-[0-9]+` (пример: `KA-42878`).
4. Спроси QA (одним сообщением):
   - «Вставь, пожалуйста, ТЗ или описание задачи <номер> из трекера — с ним анализ будет точнее. Если ТЗ нет — напиши "нет", продолжу без него.»
5. Дождись ответа. Если ТЗ нет — работай без него, но в начале отчёта пометь: «Анализ выполнен без ТЗ — сверь описание с задачей в трекере».

## Шаг 2: Сбор коммитов ветки

Собери только собственные коммиты ветки — без мержей и без того, что приехало из базовых веток:

```bash
git log --no-merges --format='%h %s' HEAD --not origin/develop origin/master origin/demo
```

- Мерж-коммиты и коммиты, попавшие в ветку при мержах develop/master/demo, исключаются автоматически.
- Коммиты других фича-веток, вмерженных в эту (например, `KA-47726` вмержена в `KA-42878`), — оставляй, это часть работы по фиче.
- Если список пуст — сообщи QA, что ветка не содержит собственных изменений (всё уже влито в базовые ветки), и остановись.

## Шаг 3: Нетто-дифф ветки

Анализируй суммарный дифф, а не каждый коммит — откаты внутри ветки схлопываются, токены не тратятся на шум.

1. Список затронутых файлов из уникальных коммитов (важно: не общий `git diff --name-only`, иначе попадут чужие файлы из вмерженного develop):
   ```bash
   git show --name-only --format= <хэши уникальных коммитов> | sort -u
   ```
2. База диффа: `git merge-base HEAD origin/develop`.
3. Нетто-дифф только по этим файлам:
   ```bash
   git diff <merge-base>..HEAD -- <затронутые файлы>
   ```
4. Если дифф очень большой (тысячи строк) — сначала `git diff --stat`, потом читай дифф частями по файлам, начиная с самых важных для логики (Java-код раньше конфигов, конфиги раньше ресурсов).

## Шаг 4: Изучение контекста — экономно

Классифицируй затронутые файлы:

- `klone-mobile-server/` — сервер
- `klone/` — клиент
- `klone-desktop/` — десктопный клиент
- XML/конфиги/ресурсы — отдельной группой

Правила изучения (токен-дисциплина):

- Основной источник понимания — сам дифф и сообщения коммитов.
- Окружающий код читай точечно: Read с offset/limit вокруг изменённого места, только когда без этого не понятен смысл правки. Не читай файлы целиком без необходимости.
- Для оценки регрессии: если изменён публичный метод/класс — Grep по его использованиям, чтобы понять, кто ещё от него зависит. Смотри только сигнатуры и ближайший контекст вызовов, не разбирай вызывающий код глубоко.
- Если в корне репы есть `graphify-out/` — используй скилл graphify для скоупинга связей вместо ручного Grep.
- ЗАПРЕЩЕНО: вычитывать модули или проект целиком, запускать gradle/build/тесты, «на всякий случай» изучать не затронутые ветки кода.

Отдельно проверь два маркера (нужны для технического приложения к отчёту, шаг 5):

- **Стейт игрока**: выпиши названия добавленных и изменённых полей в классах, которые сериализуются в состояние игрока. Проверяй только классы из диффа, ничего не сканируй дополнительно:
  - `klone-mobile-server/src/com/social/game/klonemobile/KloneGameState.java` — корень стейта, всегда входит.
  - Другие затронутые классы считай стейтом, если их объекты живут в состоянии игрока: класс (или его новое поле) хранится в поле KloneGameState либо другого стейт-объекта (например, состояние оффера, фичи). Подсказки: стейт-классы сериализуются Jackson/Model-аннотациями (`@JsonTypeName`, `@ModelTypeName`, `@ModelNeedTypeInfo`); классы конфигов с XStream-аннотациями (`@XStreamAlias`, `@XStreamAsAttribute`, `@XStreamImplicit`) — это конфиг из XML, НЕ стейт.
  - Видимость поля определяй по аннотациям и помечай в приложении:
    - `@JsonIgnore` — в базу не сохраняется;
    - `@JsonView(GameSerializerView.Full.class)`, `@ModelIgnore` — сохраняется в базу, но клиенту НЕ передаётся;
    - `@JsonView(GameSerializerView.Client.class)` — существует только для клиента: в базу не сохраняется, в стейте и его компонентах не видно;
    - без этих аннотаций — сохраняется в базу и передаётся клиенту.
  - Для каждого поля укажи класс, имя поля и одной фразой что хранит. Правки только в методах отметь как «поля стейта не менялись, правки в логике». Не уверен, стейт это или нет, — напиши об этом честно, не гадай.
- **XML**: собери список всех добавленных и изменённых XML-файлов — имя файла и полный путь от корня репы. Картинки и прочие бинарные ресурсы сюда не входят.

Если после ТЗ и диффа остались непонятные места:

- Задай QA не больше 1–3 уточняющих вопросов (просто, без жаргона).
- Что QA не знает — фиксируй в раздел «Вопросы разработчику», а не выдумывай ответ сам.

## Шаг 5: Отчёт

Выдай отчёт в чат, на русском. Структура:

1. **📋 Коротко о задаче** — 1–2 предложения: что это за фича/фикс.
2. **🔧 Что сделано** — раздельно: Сервер / Клиент / Десктоп / Конфиги (пустые группы пропускай). Человеческим языком, по пунктам.
3. **✅ Как проверить** — конкретные сценарии по основной функциональности: где в игре искать, какие шаги выполнить, какой результат ожидается. Включи граничные случаи.
4. **⚠️ Возможная регрессия** — какие соседние места могли пострадать и почему (на основе grep-анализа зависимостей). Для каждого пункта — что именно проверить.
5. **👀 На что обратить внимание** — подозрительные и хрупкие места: сложные условия, работа с датами/таймзонами, кэши, платежи и т.п.
6. **🔄 Совместимость и миграции** — только если затронуто: старые сейвы/стейты игроков, старый клиент + новый сервер, изменения протокола или моделей данных.
7. **🖥 Окружение для теста** — только если есть что сказать: нужные конфиги/XML, A/B-тесты, фичефлаги, включение через админку, затронутые платформы (iOS/Android/desktop).
8. **🚫 Что НЕ затронуто** — только если это полезно QA: где регрессию гонять не нужно, границы изменений.
9. **❓ Вопросы разработчику** — что осталось неясным и стоит уточнить перед тестированием. Если вопросов нет — раздел пропусти.
10. **📎 Техническое приложение** — единственный раздел, где технические имена приводятся как есть, без упрощения (QA использует их для проверки стейта игрока и конфигов):
    - **Поля стейта игрока** — если менялись KloneGameState или другие стейт-классы: список добавленных/изменённых полей в формате «класс.поле — что хранит», с пометкой видимости, где она ограничена: «не сохраняется в базу» (`@JsonIgnore`), «не передаётся клиенту» (`@JsonView(GameSerializerView.Full.class)`, `@ModelIgnore`), «только для клиента, в базе и стейте не видно» (`@JsonView(GameSerializerView.Client.class)`). Если менялась только логика методов — так и напиши.
    - **XML-файлы** — если были добавлены/изменены XML: список «имя файла — полный путь», с пометкой новый/изменён и одной фразой что за конфиг.
    - Если не менялись ни KloneGameState, ни XML — раздел пропусти.

### Правила языка отчёта

- Пиши для человека, который не читает код. Каждый технический термин объясни в скобках или замени описанием.
- Не «изменён `FeatureContainer.startDate`», а «поправлена логика даты старта фичи — раньше могла браться неверная дата».
- Из кода в отчёте — только названия фич, экранов, конфигов. Никаких фрагментов кода и стектрейсов. Исключение — раздел «Техническое приложение», там имена полей и пути файлов приводятся как есть.
- Не выдумывай: если не уверен, что правка делает именно это, — скажи прямо и добавь вопрос разработчику. Догадка, поданная как факт, для QA опаснее, чем честное «не знаю».

После отчёта предложи QA задавать уточняющие вопросы по любому пункту.
