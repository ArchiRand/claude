# Спек: скилл qa-branch-review

Дата: 2026-07-13

## Цель

Скилл для QA: запускается в фича-ветке (или ветке багфикса) klone-mobile и готовит понятный нетехническому QA отчёт — что было сделано, какая возможна регрессия, как и что проверять, какие вопросы задать разработчику.

## Пользователь и контекст запуска

- Запускает QA-инженер (не обязательно технически сильный) в корне репы klone-mobile, находясь в проверяемой ветке.
- Скилл живёт в `~/.claude/skills/qa-branch-review/` на этапе обкатки; после проверки на реальных ветках переносится в репу (`.claude/skills/qa-branch-review/`).
- Отчёт выдаётся в чат (без файлов), на русском языке.

## Алгоритм

### Шаг 1. Задача и ТЗ

1. `git branch --show-current`, извлечь номер задачи регекспом `[A-Z]+-[0-9]+`.
2. Если текущая ветка — develop/master/demo: остановиться, попросить переключиться на фича-ветку.
3. Спросить QA: вставь ТЗ/описание задачи из трекера. Если ТЗ нет — продолжить, но пометить в отчёте, что анализ выполнен без ТЗ.

### Шаг 2. Сбор коммитов

- Уникальные коммиты ветки: `git log --no-merges HEAD --not origin/develop origin/master origin/demo`.
  - Отсекает мерж-коммиты и всё, что приехало из базовых веток при мержах develop/master в ветку.
  - Коммиты кросс-вмерженных фича-веток (например, KA-47726 → KA-42878) остаются — это часть работы по фиче.
- Если уникальных коммитов нет — сообщить, что ветка не содержит собственных изменений, и остановиться.

### Шаг 3. Нетто-дифф

1. Список затронутых файлов: `git show --name-only --format=` по всем уникальным коммитам, объединить и дедуплицировать.
2. База диффа: `git merge-base HEAD origin/develop`.
3. Дифф: `git diff <merge-base>..HEAD -- <затронутые файлы>` — чужие изменения из вмерженного develop не попадают, откаты внутри ветки схлопываются.

### Шаг 4. Изучение контекста (токен-дисциплина)

- Классификация файлов: сервер (`klone-mobile-server`) / клиент (`klone`) / desktop (`klone-desktop`) / конфиги-XML / ресурсы / прочее.
- Основной источник — сам дифф. Окружающий код читать точечно (Read с offset/limit вокруг изменённых мест), только когда без него не понятен смысл правки.
- Для регрессии: grep по использованиям изменённых публичных методов/классов — кто зависит от правленого кода. Ограниченно.
- Инструменты структурного анализа (impact radius, граф зависимостей) — опционально, если доступны в окружении; у QA их скорее всего не будет, поэтому базовый инструмент — grep, а их отсутствие не блокер.
- Запреты: не вычитывать модули/проект целиком, не запускать build/test/gradle.
- Если что-то неясно после ТЗ и диффа — задать QA 1–3 уточняющих вопроса; что QA не знает — в раздел «Вопросы разработчику».

### Шаг 5. Отчёт

В чат, на русском, доступным языком. Структура:

1. **Коротко о задаче** — 1–2 предложения.
2. **Что сделано** — сервер и клиент раздельно, человеческим языком.
3. **Как проверить** — конкретные сценарии/чеклист.
4. **Возможная регрессия** — где и почему может сломаться соседнее.
5. **На что обратить внимание** — граничные случаи, подозрительные места.
6. **Совместимость и миграции** — старые сейвы/стейты игроков, старый клиент + новый сервер, изменения протокола/моделей.
7. **Окружение для теста** — конфиги/XML, A/B-тесты, фичефлаги, платформы (iOS/Android/desktop), нужна ли админка.
8. **Что НЕ затронуто** — границы скоупа.
9. **Вопросы разработчику** — что осталось неясным.
10. **Техническое приложение** — технические имена как есть, без упрощения: добавленные/изменённые поля стейта игрока (KloneGameState и любые затронутые диффом стейт-классы; отличие от конфигов: стейт — Jackson/Model-аннотации, конфиг — XStream. Видимость полей: `@JsonIgnore` — не сохраняется в базу; `@JsonView(GameSerializerView.Full.class)`, `@ModelIgnore` — сохраняется в базу, но не передаётся клиенту; `@JsonView(GameSerializerView.Client.class)` — только для клиента, в базу не сохраняется и в стейте не видно) и список добавленных/изменённых XML-файлов (имя + полный путь). Нужно QA для проверки стейта игрока и конфигов.

Разделы 6–8 и 10 включаются, только если есть содержание — пустых заглушек не плодить.

### Правила языка отчёта

- Каждый технический термин либо объясняется в скобках, либо заменяется человеческим описанием.
- Из кода в отчёте — только имена фич/экранов/конфигов; никаких фрагментов кода.
- Не «изменён FeatureContainer.startDate», а «поправлена логика даты старта фичи — раньше могла браться неверная дата».

## Вне скоупа

- Автоматическое получение ТЗ из трекера (MCP/API) — не сейчас.
- Сохранение отчёта в файл/артефакт.
- Запуск тестов, сборка, проверка стиля.
