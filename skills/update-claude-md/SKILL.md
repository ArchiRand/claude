Ты — технический писатель. Задача: привести `CLAUDE.md` проекта в соответствие с реальным состоянием кодовой базы. `CLAUDE.md` — это контекст для AI-агента, а не документация для людей: он должен быть точным, кратким и актуальным. Каждая лишняя строка в нём стоит токенов в каждой сессии.

Если в проекте есть и `CLAUDE.md`, и `CLAUDE.local.md` — уточни у пользователя, какой из них обновляем. По умолчанию — `CLAUDE.md`.

## Шаг 0: Определить стек

Ничего не хардкодь. Сначала определи, с чем имеешь дело, по маркерам в корне проекта:

| Файл-маркер | Стек | Где искать истину о зависимостях и сборке |
|---|---|---|
| `pom.xml` | Java/Maven | `pom.xml`: `<modules>`, `<dependencies>`, `<maven.compiler.release>` |
| `build.gradle` / `build.gradle.kts` | Java/Kotlin/Gradle | `settings.gradle*` (список подпроектов), `build.gradle*`: `dependencies {}`, `java { toolchain {} }` |
| `package.json` | Node/TS | `package.json`: `dependencies`, `scripts`, `workspaces` |
| `pyproject.toml` | Python | `pyproject.toml`: `[project.dependencies]`, `[tool.*]` |
| `go.mod` | Go | `go.mod`: модуль, версия Go, требования |
| `Cargo.toml` | Rust | `Cargo.toml`: `[dependencies]`, `[workspace]` |

Команды сборки/линта/тестов берутся оттуда же (`scripts` в package.json, `[tool.poetry.scripts]`, Gradle/Maven-таски, `Makefile`/`justfile` если есть). **Выдуманных команд в `CLAUDE.md` быть не должно** — только те, что реально существуют в конфигах.

Если маркеров несколько (монорепа) — определи, в каком подпроекте работает пользователь, и не описывай остальные без надобности.

## Шаг 1: Прочитать текущий CLAUDE.md

Прочитай целиком. Выпиши:
- Какие разделы есть.
- Конкретные утверждения об архитектуре, модулях, пакетах, механизмах.
- Упомянутые пути к директориям, модулям, пространствам имён.
- Иерархии типов и таблицы соответствий.
- Ссылки на скиллы, субагентов, внешние ресурсы.
- Команды (сборка, тесты, линт, запуск).

## Шаг 2: Проверить каждое утверждение в коде

Общие приёмы, независимо от стека:

- **Структура модулей** — файл-маркер из шага 0 (список подпроектов/воркспейсов).
- **Существование типа/символа** — грепом по объявлению (`class X`, `interface X`, `def x`, `func X`, `type X`), а не по упоминаниям.
- **Иерархии и таблицы соответствий** — грепом по признаку связи (`extends X`, `implements X`, `:` в Python/TS) и сверять **каждую строку таблицы**, не выборочно.
- **Существование директорий и путей** — `ls`/`find`, а не на память.
- **Команды** — проверять, что таск/скрипт реально объявлен в конфиге. Не запускай сборку ради проверки, достаточно найти объявление.

Не хардкодь пути — каждый раз определяй из текущего состояния проекта.

## Шаг 3: Выявить расхождения

По каждому разделу фиксируй:
- **Устарело**: символ, путь, команда упомянуты в `CLAUDE.md`, но не найдены в коде.
- **Неверно**: описано не так, как реально работает (не тот модуль, не те методы, неверная иерархия).
- **Пропущено**: есть в коде, отсутствует в `CLAUDE.md` — добавлять **только** если агент без этого сделает ошибку или будет переспрашивать.
- **Дублирует**: уже есть в глобальном `~/.claude/CLAUDE.md`, `~/.claude/rules/*.md` или в скиллах проекта — можно убрать.

Критерий важности для добавления: информация нужна агенту, чтобы не ошибиться в архитектурном решении, не нарушить принятый в проекте паттерн, не создать дублирующий механизм, не полезть в read-only зону. Не добавляй всё подряд — `CLAUDE.md` это не описание проекта, а список того, чего агент не выведет из кода сам.

## Шаг 4: Показать список изменений

Перед правкой покажи пользователю:

```
УДАЛИТЬ:
- [раздел/строка]: причина (символ не найден / модуль переехал / ...)

ОБНОВИТЬ:
- [раздел]: что устарело → что актуально

ДОБАВИТЬ:
- [раздел]: что и зачем (почему агент без этого ошибётся)

ДУБЛИРУЕТ (вынести/удалить):
- [раздел]: уже описано в <где именно>
```

Дождись подтверждения — или пропусти этот шаг, если пользователь сказал «просто обнови».

## Шаг 5: Применить изменения

Правь через Edit точечно, не переписывая файл целиком.

Принципы:
- Сохраняй структуру разделов, если она логична.
- Сохраняй инструкции по поведению агента и ссылки на скиллы.
- Убирай капитан-очевидность — то, что видно из самого кода или стандартно для стека.
- Убирай дублирование с глобальными правилами.
- Таблицы и иерархии обновляй строка за строкой по результатам грепа — не удаляй строку без проверки.
- Команды проверяй по конфигу перед обновлением.

## Что не трогать

- Инструкции по поведению агента (рабочие зоны, read-only ограничения, запреты).
- Ссылки на скиллы и субагентов — они не выводимы из кода.
- Бизнес-контекст и причины архитектурных решений (почему выбран этот механизм, зачем хотфикс).
- Неочевидные ограничения и подводные камни — именно за этим `CLAUDE.md` и нужен.

## Формат итогового ответа

```
Обновлён CLAUDE.md:
- Удалено: [краткий список]
- Обновлено: [краткий список]
- Добавлено: [краткий список]
```
