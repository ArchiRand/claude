# IntelliJ Plugin Dev — правила разработки

## Язык и версия

- Java **17** — использовать все фичи: `sealed`, `record`, `pattern matching` (`instanceof X x`),
  текстовые блоки, `switch`-выражения, `var`.
- IntelliJ Platform SDK — опираться на официальные API, не лезть в `@Internal`.

---

## Документация (Javadoc + комментарии)

**Обязательно** на каждый класс, метод, поле — кроме очевидных геттеров/сеттеров.

### Что писать

- Отвечать на вопрос **зачем / почему / для чего**, а не пересказывать код.
- Упоминать нетривиальные решения, ограничения, инварианты.
- Ссылаться на связанные классы: `{@link SomeClass}`.

### Формат — только многострочный

```java
/**
 * Один или несколько абзацев.
 * Вторая строка если нужна.
 *
 * @param foo  описание параметра
 * @return     описание возвращаемого значения или {@code null}
 */
```

**Запрещено:** `/** Однострочный комментарий. */` — всегда раскрывать на три строки минимум.

### Инлайн-комментарии

Допускаются внутри метода на сложных участках. Коротко: `// Структура PSI: аннотация → ModifierList → Class`.

### Язык

Вся документация и комментарии — **на русском**.

### Актуализация

После любой правки — проверить и обновить Javadoc затронутых методов/классов. Устаревшая дока хуже отсутствия.

## Стиль кода

### Фигурные скобки — всегда на новой строке, даже для однострочников

```java
// НЕЛЬЗЯ
if (x == null) return null;
if (x == null) { return null; }

// НУЖНО
if (x == null)
{
    return null;
}
```

Правило распространяется на `if`, `else`, `for`, `while`, `try/catch`, лямбды в несколько строк.

### Без однострочного кода

Даже простые условия — раскрывать. Читаемость > краткость.

## Архитектура и паттерны

### Кеширование PSI

Для дорогих вычислений (обход иерархии, сканирование индексов) — `CachedValuesManager`:

```java
CachedValuesManager.getManager(project).getCachedValue(
    project, KEY,
    () -> CachedValueProvider.Result.create(compute(), PsiModificationTracker.MODIFICATION_COUNT),
    false
);
```

`MODIFICATION_COUNT` инвалидирует кеш на любое PSI-изменение — это норма для плагинов.

### Мягкие ссылки (isSoft)

- `isSoft=true` → нераспознанные элементы не подсвечиваются красным. Использовать когда контекст неопределён.
- `isSoft=false` → нераспознанный элемент — ошибка. Использовать когда родительский класс точно известен.

### Dumb Mode

Перед обращением к индексам всегда проверять:

```java
if (DumbService.isDumb(project)) return null;
```

### Поиск аннотаций

Использовать `JavaAnnotationIndex` с фильтрацией по FQN — быстрее чем обход всех классов:

```java
JavaAnnotationIndex.getInstance().get(SHORT_NAME, project, scope)
    .stream()
    .filter(ann -> FQN.equals(ann.getQualifiedName()))
    ...
```

### Константы в аннотациях

Не кастовать `PsiAnnotationMemberValue` к `PsiLiteralExpression` — не работает для констант.
Использовать `ConstantEvaluationHelper`:

```java
JavaPsiFacade.getInstance(project)
    .getConstantEvaluationHelper()
    .computeConstantExpression(attr);
```

### isValid()

После получения PSI-элемента из кеша — проверять `element.isValid()` перед использованием.

## Производительность и накладные расходы

**Главное правило:** любое решение должно минимально нагружать IDE. IntelliJ вызывает провайдеры ссылок, инспекции и хендлеры постоянно — на каждый keystroke, при открытии файла, при подсветке. Некешированный полный обход проекта здесь равен зависаниям.

### Приоритет методов поиска (от быстрого к медленному)

| Метод | Когда использовать |
|---|---|
| `JavaAnnotationIndex`, `StubIndex` | Поиск Java-элементов по аннотации/имени — всегда предпочтительнее |
| `PsiSearchHelper.processAllFilesWithWord()` | Поиск текста/строки по word-индексу: только файлы с нужным словом |
| `FileTypeIndex.getFiles()` + фильтрация | Когда нужен перебор всех файлов типа — только если выше не подходит |
| Ручной обход PSI-дерева без индекса | Только в пределах одного известного файла, никогда по проекту |

### Обязательные паттерны

- **Всегда `DumbService.isDumb(project)`** перед любым обращением к индексу — иначе NPE при индексировании.
- **Кешировать дорогие вычисления** через `CachedValuesManager` с инвалидацией по `MODIFICATION_COUNT`.
- **`EMPTY_ARRAY` early return** в провайдерах — не создавать объекты ссылок на нерелевантных элементах.

### Если задачу сложно сделать оптимально

Прямо сказать об этом: объяснить почему, назвать конкретные накладные расходы, предложить 2–3 варианта с разными компромиссами между сложностью реализации и производительностью. Не замалчивать — неочевидное поведение IDE (лаги, freeze) сложнее отладить, чем предупредить.

## Аудит после реализации

После каждой реализации / значимой правки — провести аудит по чеклисту:

| # | Критерий | Что проверять |
|---|----------|---------------|
| 1 | **Производительность** | Нет ли дорогих операций без кеша? `getText()` на больших тегах? Полный обход проекта там, где хватит индекса? |
| 2 | **Память** | Нет ли хранения `PsiElement` в статических полях или синглтонах вне `CachedValue`? |
| 3 | **Нестабильность** | Обрабатываются ли `null` от PSI API? Проверяется ли `isValid()`? Защищено ли от Dumb Mode? |
| 4 | **Нагрузка на IDE** | Не создаются ли лишние провайдеры/обработчики на нерелевантных файлах? Есть ли `EMPTY_ARRAY` early return? |
| 5 | **Расширяемость** | Легко ли добавить новый тип ссылки или новую аннотацию? |

Результат аудита — сформулировать как список найденных проблем и предложить фиксы (или сказать что всё ок).

## Проактивные предложения

Если в процессе разработки замечено что-то полезное, чего автор не просил —
**предложить и объяснить зачем**. Примеры поводов:

- Очевидная, но отсутствующая фича (completion, inspection, quickfix)
- Потенциальная утечка памяти
- Паттерн, который упростит будущее расширение
- Случай, который текущий код не обрабатывает (edge case)
- **Не принимай решение за пользователя там, где есть неоднозначность — предложи выбор.** Попап это лишь один из способов реализации. Когда пользователь предлагает или просит реализовать какое-то решение — оцени его с точки зрения целостности как решения и удобства использования для пользователя.

Предлагать коротко, не навязывать.

## Коммиты

- Разбивать по **логическим блокам** (одна задача — один коммит).
- Сообщение на **русском**, развёрнуто но не более **200 символов**.
- Формат: `тип: что сделано` → `fix:`, `feat:`, `refactor:`, `docs:`, `chore:`.
- **`git push` — запрещён.** Никогда не пушить без явной команды.

Пример хорошего сообщения:
```
feat: навигация с дочернего XML-тега на поле Java-класса через XStreamTagFieldReference
```
